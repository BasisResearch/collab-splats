# 018 — SfM backends: colmap + hloc beside instantsfm

Date: 2026-09-26 · Status: accepted · Branch: `feat/sfm-backends`
([spec](../specs/2026-09-26-sfm-backends-design.md) ·
[plan](../plans/2026-09-26-sfm-backends.md))

## Context

- `ColmapCreator` and `HlocCreator` existed in `pointcloud/sfm/` but nothing dispatched to them
- `instantsfm` was the only `pointcloud.method: sfm` backend; config validation rejected the others

## Decision

- both wired through `SFM_CREATORS` (dict in `collab_splats.pointcloud.sfm`), the table
  `Reconstructor._run_sfm` dispatches on
- incremental mapping only (`pycolmap.incremental_mapping`), no `mapper` key
  - the system colmap is 3.10-dev, which has no `global_mapper`
  - instantsfm already covers global SfM
- one shared `pairing` vocabulary for both backends:
  `sequential | retrieval | sequential+retrieval | exhaustive`
- one shared SIMPLE_RADIAL camera per scene, refined by the mapper — the same camera freedom as
  instantsfm, so the A/B is fair
- a registered-subset floor (`min_registered_frac`, default 0.5) for colmap/hloc only
  - above it: frames the model did not register are dropped, with a warning
  - below it: `RuntimeError` with N/M
  - instantsfm stays strict

## Dependency

- hloc is an editable uv **path** source on `third_party/hloc` @ `c13273b`
  (`c13273bd0ecc2917a35910fd843712a1c6243193`), optional extra `hloc`; not a git install
  - `setup/hloc.sh` clones it (`--recursive`) and re-pins every run; `--prefetch` caches weights
  - a path source must exist before any resolve: run `setup/hloc.sh` before `uv lock` / `uv sync`
- why editable: SuperPoint/SuperGlue `sys.path`-append `../../third_party` for the SuperGlue
  submodule (`hloc/extractors/superpoint.py:8`, `hloc/matchers/superglue.py:6` @ `c13273b`);
  a git install ships only the `hloc` package
- vismatch rejected: not in the venv, and its COLMAP export is mid-rework (`vismatch-fork`)
- colmap retrieval pairing uses COLMAP's `vocab_tree_flickr100K_words32K.bin`
  - pre-3.12 format a 3.10 binary reads; sha256
    `d37d8f19ee0a49705c4c0b06967a08cedfed5cf86519eada3271497256732bc2`
  - fetched once into `~/.cache/collab_splats/`, hash-checked on every use

## No GLOMAP

- needs the COLMAP >= 3.11 / 4.x CLI; the image ships 3.10-dev
- follow-up: a COLMAP 4.x Docker image, then `mapper: global`

## Consequences

- colmap's `sequential+retrieval` is not hloc's
  - colmap: sequential pairs + periodic loop detection (every `loop_detection_period` frames)
  - hloc: sequential pairs unioned with per-frame retrieval
  - so colmap vs hloc compares pipelines, not matchers
- colmap features come from the colmap 3.10 CLI, mapping from pycolmap 4.0.4
  - zarr attrs record both: `pycolmap_version` + `colmap_cli_version`
  - hloc records `pycolmap_version` + `hloc_commit` (`HLOC_PIN`; `hloc.__version__` is "1.5")
- `uv.lock` is NOT regenerated by this work: the user runs `setup/hloc.sh`, then `uv lock` +
  the sync
- the colmap default pairing (`sequential+retrieval`) pulls the 15.2 MB vocab tree on first use

## Results

- **not run.** The integration runs (instantsfm / colmap / hloc through `Reconstructor`) and the
  wrapper tests were not run: the venv lacks `nvdiffrast`, so `collab_splats.wrapper` cannot
  import. No registered counts, point counts, reprojection errors or PSNRs exist yet.
- hloc also waits on the user's `uv lock` + sync
